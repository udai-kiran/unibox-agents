## Query quality

- Read the schema and service queries. Use the database and ORM patterns already
  present in this repository. Check the target version before choosing features.
- Write clear SQL with explicit columns, joins, and predicates. Prefer set-based
  operations. Use CTEs when they improve clarity, not as automatic extra layers.
- Check NULL behavior, join row multiplication, duplicate handling, and empty
  results. Do not use DISTINCT to conceal an incorrect join.
- Make ordering explicit when it matters. Use deterministic tie-breakers for
  pagination and deliberate inclusive or exclusive date and time boundaries.
- Inspect SQL generated by the ORM for important queries. Check repeated queries,
  unnecessary columns, large result sets, and unexpected database access.

## Schema and data integrity

- Keep money in integer minor units. Avoid floating-point money and implicit conversions
  that change exact totals. Preserve the app's domain keys and data contracts.
- Use primary keys, foreign keys, NOT NULL, UNIQUE, and CHECK constraints for
  important invariants. Define deletion behavior and timestamp semantics clearly.
- Use normalization by default. Add JSONB, denormalized data, or partitioning only
  when the actual workload justifies it.
- Module schemas must not import another module's schema. Use the shared schema
  layers directly for cross-domain references. Keep the project's single schema
  entry point for migrations.
- Add new tables to any backup or export lists the project keeps and keep backup
  coverage checks passing.

## Transactions and concurrency

- Keep database access in services with explicit database or transaction handles.
  Use transactions for changes that must succeed together and preserve rollback
  on failure. Avoid slow external calls or user interaction inside transactions.
- Use constraints, atomic updates, or appropriate row locks to prevent races.
  A check followed by an insert alone does not prevent duplicate records.
- Choose isolation and locks for the required behavior. Keep lock duration short,
  use consistent lock order, and check lost updates, deadlocks, and partial writes.
- Retry deadlocks or serialization failures only with a safe, bounded policy for
  the whole transaction. Account for duplicate requests and external side effects.
- Return connections promptly and respect pool limits. Do not share transaction
  state across concurrent work unless the driver and design support it.

## Plans, indexes, and scale

- Measure important performance changes with representative data and query plans.
  Check row estimates, actual work, scans, joins, sorts, buffers, and disk spills
  where available. A sequential scan alone is not a defect.
- Choose indexes from real filter, join, and ordering patterns. Consider composite
  column order, selectivity, existing indexes, storage, and write costs.
- Use EXPLAIN for initial plan inspection. EXPLAIN ANALYZE executes the statement;
  run it only where executing that query and its workload is authorized and safe.
- For large results, use appropriate pagination, streaming, or bounded batches.
  Consider keyset pagination when large offsets become expensive. Make backfills
  restartable and validate affected row counts and invariants.

## Migrations and recovery

- After schema changes, run npm run db:generate and inspect the SQL, snapshots,
  and migration metadata. Preserve data and constraints; avoid unrelated changes.
- Check compatibility with the current and updated app. Split expansion, backfills,
  and removal into separate steps when a single change would break running code.
- Assess locks, table rewrites, index creation, and backfill costs. If using
  CREATE INDEX CONCURRENTLY, respect its restriction on transaction blocks and
  check that the migration runner supports the required execution.
- Describe recovery for significant changes. Do not assume a reverse migration
  restores deleted data or that a backup exists and is usable.
- Apply migrations only when authorized, against the intended database as the
  application's database role. Do not apply them as a superuser or disable integrity checks
  to bypass failures.

## Ownership and database safety

- Filter user data by userId for reads and writes, including joins and bulk work.
  Keep permissions consistent with the existing app; do not introduce privileged
  paths that bypass user ownership.
- Parameterize values. For dynamic identifiers or sort choices that cannot be
  parameters, use explicit allowlists and safe identifier handling.
- Keep credentials and private user data out of logs, query traces, reports,
  and exports. Use the existing database roles and secret handling.
- Verify the environment and intended scope before database execution. Do not
  use destructive statements as exploration, run live mutations or heavy workloads
  without authorization, or assume rollback removes every external effect.

## Verification

- Test changed behavior in proportion to the risk. Include relevant NULL, empty,
  duplicate, boundary, join, ownership, constraint, and transaction cases.
- Use an isolated database of the same engine for engine-specific checks. Test concurrency,
  rollback, migrations, and recovery when relevant; never use production for tests.
- Run relevant project type checks, lint, and tests. Review the SQL and schema
  diff, generated migrations, and backup coverage. Do not weaken constraints
  or tests to make checks pass.
- Report query plan evidence, actual measurements, and checks that were not run.
  Keep predictions separate from measured performance or verified migration safety.
